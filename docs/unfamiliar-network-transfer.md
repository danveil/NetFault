## Short learner guide draft

1. Define the failing service, source, destination and what still works.
2. Inspect host addressing and local interface state.
3. Test the nearest boundary using a useful working control.
4. Follow the expected path outward; record what each observation rules out.
5. Distinguish a route from permission to forward. Check the return direction too.
6. Compare control-plane information with actual delivery; one successful ping proves only that test.
7. Change one justified setting while preserving the design and record how to undo it.
8. Collect fresh state and service evidence after the change, including reciprocal and required negative controls.

No mandatory protocol order, scored hypothesis or command unlock. In a future app entry this should be short, available before investigation and free of scenario-specific addresses, fault locations or expected evidence lists. Optional notes can hold hypotheses using existing journal notes; no new efficiency/intelligence score or unsupported claim about unnecessary commands.

## Public/private and mode contracts

Public data may contain neutral identity, incident, service targets, physical topology/design and the same relevant capability set for both possible fault families. The set describes what can be inspected/edited, never what is wrong. Do not publish a hidden-family enum, single-family repair panel mapping, accepted repair, evidence rubric or hint in catalog metadata, client comments or initial responses. Plain technology configuration observed through a legitimate diagnostic is evidence, not a prohibited secret.

Private scenario data owns the selected fault, minimal correction, baseline requirements, healthy invariants and grading. Assessment must retain server-owned history, replay, expiry, immutable finalization, no-store and durable CAS. Use existing storage and Windows retries; validate a device against the session's scenario, not a user-supplied scenario or fixed name list.

Explicit Practice packs are intentionally inspectable and cached in local storage for offline execution. No frontend hiding can make an identical offline Practice answer secret from its owner. Assessment's hidden-family claim must therefore be scoped to its public assets/initial attempt and ordinary investigation, not exam-grade isolation from separately downloaded Practice data. Preserve the current honest educational security boundary.

Practice should support exploration, trials, journal, requested explanation and repaired preview. Assessment remains online, without hints/reveals during an attempt. Keep the current service-worker architecture; complete real offline reload/trial/grade/save/reopen testing for each newly implemented pack. Do not report offline Assessment.

## Verification contract for a future implementation

- **Original evidence:** authentic command/source/output observations from the original version, sufficient to distinguish the hypothesis from working controls.
- **Repair:** exactly one intended semantic correction; reject unrelated route/address/policy bypasses and preserve all healthy technologies.
- **Fresh state:** current-version configuration and relevant derived operational state; stale or canonical-preview observations cannot count.
- **Fresh behavior:** intended forward and return service plus retained negative policy/isolation controls where applicable. An applied change alone is recovered-but-unverified.
- **Alternative paths:** allow genuinely equivalent observations, not arbitrary keywords or one hardcoded command sequence.
- **Persistence/privacy:** renamed-device API access, new pack identity, old journals/revisions, concurrent duplicate edits, deadlines, replay and static asset/initial-response scans.
- **Mobile:** explicit graph layout, no node/control intersection or clipped labels, readable terminal wrapping, no page overflow, 44px controls and tap selection at desktop, 414px and 360px. Do not shrink a graph until labels become unreadable.

Existing timing/history/repair-count telemetry may be described factually; do not infer wasted effort or score intelligence/mastery. Optional hypotheses should remain ungraded and nonblocking if later added. No telemetry feature is added by this audit.
