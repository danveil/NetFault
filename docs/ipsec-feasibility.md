## Discrepancies retained and qualified

1. **V27/28 rechecked visually:** configuration destination `198.133.219.87`; displayed destination `209.165.201.2`. They are inconsistent or separate examples. No canonical paired configuration is invented.
2. V3/VR broadly equate VPN with encryption; V16 explicitly calls GRE non-secure, and provider VPN separation is distinct. Teach the mechanism and boundary, not the label.
3. V16–17 blanket multicast limitations conflict with V21's explicit IPsec VTI multicast support. Qualify conventional policy-based descriptions rather than requiring GRE universally.
4. V12–13 IPsec/SSL strength/application tables are dated comparisons, not universal rankings or current product advice.
5. V33 broadly says ESP supplies both services; V32 acknowledges no encryption is possible. [RFC 4303 §1](https://www.rfc-editor.org/rfc/rfc4303.html#section-1) distinguishes service combinations. An ESP label is insufficient evidence of confidentiality.
6. V37 confuses HMAC key length with MD5/SHA-1 digest length. [RFC 2104 §2–3](https://www.rfc-editor.org/rfc/rfc2104.html#section-2) defines variable key handling. An unkeyed hash alone does not authenticate origin.
7. V43 identifies DH group 24 as ECC and calls it preferred next-generation encryption. [RFC 5114 §3.2](https://www.rfc-editor.org/rfc/rfc5114.html#section-3.2) identifies IKE group 24 as 2048-bit MODP with a 256-bit subgroup. DH agrees key material; it is not bulk encryption or identity proof by itself. No present-day group recommendation is made here.
8. V34–35 break-time and algorithm rankings are not reproduced as validated modern performance/security facts. The role taxonomy is useful without teaching obsolete deployment settings.

Primary [RFC 4301](https://www.rfc-editor.org/rfc/rfc4301.html) distinguishes security policy, protection/bypass/discard and traffic processing. A crypto selector and a forwarding ACL can both match fields but have different consequences. This reference check is neither course evidence nor device execution.

## Existing implementation seams

Inspected `engine.ts`, `acl.ts`, `nat.ts`, `gre.ts`, `gre-grading.ts`, repair replay, schema/catalog, private registry, server sessions/store, API no-store headers, privacy browser test and topology/Academy boundaries:

- IPv4 RIB lookup, physical traversal and source-aware probes could support transport controls. GRE separates outer receiver delivery from inner forwarding/replies. It deliberately has no protection provenance or IKE negotiation.
- LAB 009 standard ACLs match only source and decide permit/drop. They are **not crypto selectors**; changing their semantics would break existing policy learning.
- LAB 013 changes packet identity at specific ingress/egress stages. NAT does not provide protection and the bounded case rejects mixed models. Its helpers cannot resolve NAT/IPsec ordering by assumption.
- Repair versions, replay, authentic observations, fresh grading, reciprocal verification, private scenarios, no-store routes and durable Blobs/CAS are reusable infrastructure, not a security protocol model. Windows bounded session-write retry is unchanged.
- A new model would still need explicit protection provenance, transmit/receive policy, actual peer delivery and independent protected replies. Route success plus equal config strings cannot by itself justify real SA establishment.
- Existing Academy already provides bounded diagrams, validated tap choices, revisions, requested solutions and offline public content. This is sufficient for the supported conceptual gap, without private cases or server changes.

These faults are technically plausible. None is rejected simply because it is hard to implement; collectively their configuration-to-state evidence is weaker than the role/concept evidence, while an equality-only implementation would add false confidence. Mobile cards and structured repair are available, but UI feasibility is not protocol feasibility.

For peer/PSK/proposal faults, single-field repairs would fit mobile cards and deterministic grading, but authoritative peer/authentication/compatibility observations must first exist; a matching label is not sufficient proof. Selector and attachment faults have stronger policy-reasoning value, but need explicit direction and protect/bypass behavior: grading must reject unprotected delivery, and mobile evidence must display both directions without hiding policy fields. Underlay failure has the lowest new engine/regression cost and clearest route diagnostics, but weak novelty. GRE-without-protection has high transfer value and highest interaction/regression risk here; grading would need independent protection provenance beyond existing GRE success. Each candidate would require original observations, the minimal correction and fresh reciprocal protection/delivery proof, with private case bindings on the server. These are feasibility criteria, not implemented grading rules.

## Gate and delivered alternative

The optional **UNEXECUTED** companion asks for real authorized platform/version/output evidence and readable activity instructions, without pretending to supply the uninspected PKA answer.

Before reconsidering an executable case, obtain/inspect readable practical instructions or a controlled documented device experiment defining endpoints, policy selection, authentication/proposal compatibility, application/attachment, receive behavior, protected delivery and observations. Then choose a single minimal fault and define fresh bidirectional protection evidence, bypass rejection and independent model negatives. This is a future gate, not automatic next-milestone authorization or a reason to implement real crypto.

IPsec construction, actual SA/traffic inspection, fault repair, secure algorithm selection and independent platform transfer remain unverified; remote-access clients, VTI/DMVPN, NAT-T, fragmentation, lifecycle/rekey, anti-replay and advanced combinations remain outside the engine.

Revised rough ANT **learning-support estimate: ~89%, uncertainty approximately ±5 percentage points**. Applying the prior explicit planning rubric: conceptual source support **34/35** (was 33), structured practice **24/25**, executable breadth **22/25**, practical preparation paths **9/15** = **89/100**. Only conceptual support changes; six exercises do not justify claiming more executable or authentic device competence. These are judgmental planning ratings, not measured syllabus weights, mastery, exam score, predicted grade or probability of an A. The practical PKA uncertainty warrants the wide range. Remaining major gaps include broader IPv6/OSPFv3, dynamic NAT/PAT, IPsec/WAN operation, design/security variants, real QoS/controllers and unfamiliar-network transfer.
