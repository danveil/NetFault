### Source qualifications and technical cross-check

- N8's destination-based wording is not a general algorithm for inside-source matching. The proposed model explicitly separates route lookup from source matching.
- N25's broad assertion that NAT does not allow outside-initiated requests conflicts with its own static examples N14/N20. Explain this as a dynamic/PAT context limitation; do not teach it as a restriction of permanent static one-to-one mappings.
- N22 labels PC2 `192.168.10.11` alongside `192.168.11.0/24`. N23 depicts 192.168.x hosts but selects `10.0.0.0/8`. N24 depicts outside `.225` while its table uses `.226`; its displayed overload line also lacks the `inside` word present in R. Do not copy these as a coherent working configuration or an intentional assessed fault.
- N4/N9 address hiding is not authentication or a firewall guarantee. N10 performance/general implementation claims are not modeled timings. N19's comparison uses “NAT” for address-only translation while PAT is itself a NAT form.
- Source images establish teaching content, not actual success on the learner's Packet Tracer version. Remaining nonlisted slide images were not independently reviewed; no new requirements are inferred from them.

## 2. Smallest useful model

| Option                 | Course support     | New machinery                                                                                                                 | Educational value and decision                                                                                                                                                              |
| ---------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Static one-to-one   | N7, N13–14, N20, R | Packet address context, ingress role, reversible pair, actual delivery endpoint; no ports or allocation history               | **Select.** Teaches identity versus routing, both directions, and evidence-based correction. Substantial forwarding change but bounded and replayable                                       |
| B. Dynamic without PAT | N15, N21–22, R, X2 | Pool ownership, deterministic allocation order, exhaustion, release/reset rules, persisted/replayed allocation events         | Strong next topic, especially X2, but more than needed for the first NAT case. No port model required, yet history is essential; a permanent prefilled table would misrepresent dynamic NAT |

**Static mapping needs no persistent runtime translation state.** The permanent entry derives from the current configuration version. A probe carries temporary address changes and delivery metadata; that is not a dynamic session table. No clocks, allocation or expiry are added. Existing durable repair/observation history is sufficient across serverless invocations.

Current conceptual flow is source selection → local delivery check → gateway/route → outbound policy → next-hop L2 exchange → next device, repeated, followed by separately routed reply. It is not a generalized packet pipeline.

Proposed schema-12 branch must carry original and current source/destination, ingress interface, actual delivered device/interface and translation steps. After **successful L2 delivery** to R1 outside, reverse destination translation precedes its lookup. After ingress on R1 inside, route lookup selects outside egress before source translation. Every next hop still needs physical resolution/delivery. Return generation uses the request's **delivered source and destination**, then validates restored response identity at the initiating host. Details and failure examples are in [the exact contract](milestone-3n-plan.md#3-packet-and-routing-contract).

Do not reuse HSRP `virtualOwner` to make R1 answer echo requests addressed to the inside global. That address represents PC-A; it is neither a router service nor a new connected endpoint. Keep old no-NAT forwarding behavior isolated and regression-tested. Do not “fix” older schema reply conventions incidentally.

ACL source classification is excluded. LAB 009's source-only outbound filtering must stay separate and unchanged; future matching reuse cannot turn a NAT nonmatch into an ACL deny. Reject NAT combined with ACL/HSRP/STP/port-security/LACP/OSPF in the first schema. Ordinary failed link/L2 resolution must still stop delivery before ingress NAT. Simple static routes avoid a second protocol fault.

Exclude dynamic pools, PAT, ports, ICMP identifier allocation, flow expiry, NAT64/NPTv6/IPv6 NAT, twice/policy NAT, route maps, VRFs, hairpin NAT, on-link global proxy ARP, NAT of router-originated probes, ICMP error/quoted-header translation, stateful firewall, packet capture, generic IOS parsing, topology builder and additional labs. These are honest first-model limits, not claims about what real NAT permits.

## 6. Decision and residual uncertainty

PASS means the bounded extension can be delivered in 3O with **model tests before scenario/UI work**. It does not mean a cosmetic output change is sufficient. The packet context/return ownership seam is substantial, but it requires neither a separate transport subsystem nor new durable state, so a separate foundation milestone is not necessary for this scope. Stop and revise that verdict if implementation cannot preserve old behavior or begins requiring flows, proxy ARP or ICMP errors.

Remaining uncertainty is external fidelity: exact Packet Tracer/router image command support and transient table rows have not been executed. The proposed display is explicitly a static educational subset. The course's integrated dynamic NAT practical remains outside scope. Public Practice packs and repository authoring docs can expose case answers; server-backed self-assessment is not a secure examination. The next specification contains the privacy, source-validation, test and stop gates.
