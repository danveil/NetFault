## 3. GRE, VPN and IPsec decision

A useful first WAN investigation can focus on **GRE alone**: V24–28 supply independent purpose, configuration and verification material. VPN describes an application/design category; GRE supplies encapsulation; IPsec supplies separate security mechanisms. Adding IPsec would require cryptographic policy, peer authentication, negotiation/security-association state and additional failure evidence unrelated to this one endpoint error. Course support for GRE is sufficient without using the uninspected PKA as proof. IPsec/VPN security remains a separate later milestone; no confidentiality, authentication or secure-tunnel badge belongs in LAB 014.

Primary technical checks, reviewed 28 September 2026, complement rather than replace course evidence:

- [Cisco GRE interface states](https://www.cisco.com/c/en/us/support/docs/ip/generic-routing-encapsulation-gre/118361-technote-gre-00.html), “What Determines the Tunnel Interface State”: local source and a route to the destination can retain line-up without successful remote delivery; recursive resolution is a distinct failure. This supports separating local state from transport tests, not importing its entire platform state machine.
- [Cisco GRE keepalives](https://www.cisco.com/c/en/us/support/docs/ip/generic-routing-encapsulation-gre/118370-technote-gre-00.html), Background: unprotected GRE has no peer-liveness negotiation; keepalives are an optional additional mechanism, excluded here.
- [Cisco IOS XE Implementing Tunnels](https://www.cisco.com/c/en/us/td/docs/routers/ios-xe/ip-routing/b-ip-routing/m_ir-impl-tun-xe.html), “Configuring a GRE IPv4 Tunnel” and its example: separate source/destination devices, physical-interface or address source, reciprocal outer endpoints. The future model deliberately limits receiver matching to one fixed point-to-point pair; it does not claim every Cisco platform's decapsulation behavior.
- [RFC 2784](https://www.rfc-editor.org/rfc/rfc2784.txt), sections 2–4: payload/carrier distinction, IPv4 payload forwarding after decapsulation and IPv4 protocol 47. Header bytes, payload TTL behavior and fragmentation are not implemented by the proposed logical journey; it must never be presented as a packet capture or accurate traceroute.

No Packet Tracer, IOS, CML/GNS3, physical router, phone or live Netlify experiment was run. The exact proposed network remains externally UNEXECUTED.

## 6. Selected design and state separation

Exactly one title: **The path above**. Exactly one fault: R1 Tunnel0 points to the transport router's reachable `198.51.100.1` instead of R2's `198.51.100.2`. Both local tunnels can remain up/up and their overlay routes installed. The wrong endpoint responds to an ordinary underlay ping but is not a configured GRE receiver. This is not a missing-route, encryption or negotiation failure.

Five devices suffice: PC-A — R1 — T1 — R2 — PC-B, with a separate R1/R2 Tunnel0 design annotation. No switch, cloud object masquerading as a routing engine, extra path or second tunnel is needed. The [exact plan](milestone-3p-plan.md#2-topology-addresses-and-sole-fault) defines all addresses and routes.

Model three separate questions: (1) local administrative/source/routability state; (2) directed physical transport delivery to the configured outer address; (3) directed receiver match plus inner forwarding and an independently routed reply. No global “tunnel healthy” boolean should answer all three. **No remote liveness is modeled.** A snapshot transport result is an evaluation for that packet, not a keepalive observation. Receiver matching is the explicitly bounded point-to-point endpoint contract, not authentication or a negotiation exchange.

Recursive destination-through-self routing is excluded and rejected by supported-model validation. Underlay prefixes cannot overlap overlay route/tunnel prefixes. A missing physical endpoint route is a representable runtime/model-test failure; it must not be silently supplied by the logical tunnel. Trace is excluded from this lab because the current flattened hop abstraction cannot honestly combine outer transport and inner TTL behavior. Post-submission journey diagrams may show nested logical/physical segments with an explicit non-trace label.
