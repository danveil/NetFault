## Evidence and classification

This is an audit of the current implementation, not of every real Cisco combination. SAFE means a supported narrow composition; SAFE WITH LIMITS means the listed restrictions are mandatory. NOT CURRENTLY SAFE means the schema rejects the combination or its cross-model semantics are unimplemented. Removing a validator is not evidence of safety.

Reviewed all executable families in `engine.ts`, `ipv6.ts`, `etherchannel.ts`, `acl.ts`, `stp.ts`, `hsrp.ts`, `port-security.ts`, `nat.ts`, `gre.ts`, their validators/graders, scenario schema, repair replay, preview, catalog, topology, client workflow, API, sessions/store, local persistence, service worker and regression tests. The [23 audit tests](../tests/composition-audit.test.ts) demonstrate selected successful compositions and explicit rejection boundaries. Their fixtures modify existing private cases for engineering tests; they are not independent learner scenarios, new topology designs or new assessment rubrics.

## Forwarding audit

`routes` installs connected/local routes, selects static ownership ahead of OSPF for an equal prefix, and computes per-area OSPF paths. `lookup` uses longest prefix. VLAN-aware `peers` supplies next-hop reachability; schema-9 traversal uses settled STP links, while schema-7 LACP replaces bundle members with derived logical forwarding. These are separate supported branches, not a composed STP-over-port-channel graph.

For the tested ordinary IPv4 composition, route selection precedes outbound ACL evaluation. The filter sees the forwarding packet source; router-originated traffic skips that router's own egress ACL in this bounded model. Source-aware controls must therefore originate upstream and traverse the filtered router. Replies are evaluated independently. OSPF adjacency computation does not model ACL-filtered routing packets, which is why the safe ACL location here is a LAN data egress away from the point-to-point transit.

NAT ingress destination translation occurs before local delivery/route lookup; inside-to-outside source translation follows egress selection. Actual delivered identities seed the reply. An existing configured translation cannot manufacture an outward route or the remote route to the global identity. Although shared forwarding contains an ACL step after source translation, mixed NAT/ACL is rejected; this code order alone cannot establish vendor-general ordering or all required controls.

GRE selects a logical route only when local physical-source/routability conditions hold. Outer forwarding runs with physical routes; the actual delivered receiver must match the opposite endpoint before inner forwarding resumes. Both source/destination ownership and the return path matter. No teleporting, encryption, keepalives or IPsec state. GRE validators require the same graph shape as LAB014, so changing only names/addresses would fail 3U's topology-transfer requirement.

HSRP resolves a virtual next hop to its derived active member and virtual MAC under its isolated shared-access topology. Port-security admission uses separate directed Ethernet checks. IPv6 uses its own neighbor ownership and forwarding switch. These mechanisms are implemented, but cross-composition beyond their validators is not established.

## Executed composition evidence

The audit suite adds **23 passing tests**:

- Seven for schema-valid access VLAN + point-to-point OSPF + LAN ACL: healthy neighbors/routes/local gateway, blocked service, applied ACL repair with reciprocal delivery and excluded source retained, wrong VLAN isolation, absent OSPF route, independent missing return advertisement, static-over-OSPF prefix ownership and diagnostic output.
- Four for NAT/routing and GRE/routing: successful controls followed by independently removed outward/return or underlay/overlay routes. Translation/tunnel intent cannot replace missing forwarding state.
- Eight rejection cases: NAT with ACL/OSPF; GRE with ACL/NAT; HSRP with ACL/OSPF; STP with channel state; IPv6 with IPv4 ACL state.
- Four repair-contract checks: no accepted VLAN/OSPF/static route trial action, and a canonical static repaired preview is not a learner-applied configuration trial.

These results establish the named fixture behaviors, not arbitrary model composition or complete device equivalence. Existing suites also cover STP, LACP, virtual ownership, port admission, persistence, source-aware probes, epochs, CAS and Windows write retries. See [fresh verification](verification.md).

## End-to-end challenge blockers

1. **Second fault family and fresh repair:** `repairActionSchema`/persisted repair unions contain LACP, ACL, STP, HSRP, port security, NAT, GRE and IPv6 actions, but no access-VLAN, OSPF or static-route actions. Those early lab branches grade diagnosis/proposed repair and use canonical `repaired()` previews. That is their established contract, not an existing lab defect. Copying it would fail 3U's applied-change/latest-version verification requirement. In the strongest tested mixed composition only ACL order has the complete existing trial path.
2. **Version binds capabilities to fault family:** access-VLAN repair requires v3; ACL state requires v8; NAT/GRE/HSRP/STP each have separate guarded versions and graph contracts. Moving a fault into a new combination requires an explicit validated authoring/trial/grading contract, not a version-number substitution or blanket loosening of guards.
3. **Neutrality/privacy:** public IDs, topic labels, case-specific cause/fix lists and `isAcl`/`isNat`/etc. control selection identify the current lab family. Neutral titles alone would not satisfy the new hidden-family requirement. A single exposed repair kind can reveal the fault. Existing privacy tests protect private text/values, not family indistinguishability. This is a stricter new requirement, not a claim that old assessments promise hidden topics.
4. **Unfamiliar identities and graph:** `/api/lab` command validation enumerates existing device names despite later session-owned membership checking. Default topology positions/handles cover fixed indices, with explicit old-case variants; simply adding a larger graph can leave positions undefined. Both need bounded, public topology/capability descriptors validated independently of the private fault.

The valid schema-8 audit fixture is **not** a production scenario: its inherited rubric was not redesigned to assess every new healthy subsystem, its Access identity is not accepted by the current public command route, and it is never registered or served. Passing a direct engine call is not end-to-end readiness.

## Gate and smallest foundation

**DEFER**, rather than PARTIAL: PARTIAL still requires two strong, different-fault challenges with neutral controls, fresh trials and unfamiliar topology. One promising ACL composition is insufficient. NAT/ACL and composed WAN options are guarded out; readdressing fixed NAT/GRE/LACP topologies or claiming their required routing/VLAN plumbing as a new pack would be filler.

This is not a claim that a broad forwarding rewrite or new protocol engine is necessary. The smallest proposed foundation stays within tested access VLAN + point-to-point OSPF + LAN ACL:

1. Add an explicit bounded composition contract without changing old revisions or widening NAT/GRE/STP/HSRP. Define legal acyclic graph, transit/ACL locations and addressed ownership.
2. Add one replayable access-VLAN repair action alongside existing ACL sequence repair, with strict existing port/VLAN validation, no-op semantics, preserved unrelated state, persisted epochs and server replay. This supplies two candidate fault families without new forwarding algorithms.
3. Provide the same bounded multi-family investigation/repair capabilities regardless of hidden fault; generic cause choices, neutral IDs/topics, scenario-owned device validation, and no correct-repair binding in public data. Keep unsupported choices honest and server-validated.
4. Define private recovery contracts requiring authentic baseline, minimal invariant-preserving change, latest-version state, reciprocal delivery and policy controls. Retain recovered-but-unverified; canonical preview never supplies evidence.
5. Add explicit responsive public graph positions/edges and validate all node indices. Test renamed devices through the API and mobile selection before authoring larger cases.

These are recommended follow-up foundation changes, **not implemented or automatically started**. No new authentication, persistence architecture, worker, arbitrary CLI, random generator or protocol engine is required. Re-run the gate after that foundation; only then author two original scenarios under the [transfer contract](unfamiliar-network-transfer.md).
